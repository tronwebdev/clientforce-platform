## AddFieldDrawer

AddFieldDrawer (testid `bold-drawer-field`) — /home/user/clientforce-platform/apps/web/components/bold/settings/BoldCoreDrawers.tsx:149-226

OWNER RULING APPLIED: the prototype governs style and anatomy, not capability; a toast is not a replacement for a mutation; a function with no replacement is a BLOCKER, not a deletion.

VERDICT: no BLOCKERs, and no non-prototype drawer needs to be carried. Every one of the 15 functions is re-expressed in ONE prototype idiom — `add-drawer` (the ADDFLOW wizard), plus a `confirm` for the one destructive path and a `toast` for the one purely informational one. The drawer survives, but as the prototype's own container rather than as a build-invented one.

WHY add-drawer is the honest idiom, not a force-fit. AddFieldDrawer is already structurally identical to addDrawer (Console Bold.dc.html:4886-4918): eyebrow + title + step body + one field per step + Back/step-indicator/primary + a final step that writes and closes. The prototype's ADDFLOW map (:4877-4889) contains exactly four families — addsender.email, addsender.num, addsource.def, addfact.def — and no field family, which is why `add()` for that tab falls through to `this.flash('New field')` (:4972). That fall-through is an unfinished branch in a design artifact, not a decision to make field-creation a toast: the same file already routes the three sibling adds on the SAME item page into real wizards. The fix is to register a fifth family, not to build a new container and not to delete the function.

Why inline-edit cannot substitute. Creation needs a name AND a value before any row exists, and the name is what derives the storage key (`workspaceFieldKey` → `field_<slug>`, packages/core/src/workspace-settings.ts:72-79). There is no row to put a dashed-underline input on until the write has already happened. Inline-edit is the right idiom for what comes AFTER creation, and that path already exists (see next note).

SOLE-PATH FINDING (the reason this drawer cannot simply be dropped). `POST workspaces/fields` has exactly one call site in the repository: bold-settings-live.ts:31-32, reached only from BoldCoreDrawers.tsx:159. Nothing else in the web app, the guided build, or onboarding mints a `field_*` key. Delete the drawer without the ADDFLOW replacement and named-field creation leaves the product entirely.

WHAT IS *NOT* LOST WITH THIS DRAWER (checked, so it is not double-counted). Once a field exists, `isWorkspaceFactKey` matches the `field_` prefix (packages/core/src/workspace-settings.ts:58-60), so the created row is fully editable (PATCH workspaces/facts, both label and value) and removable (DELETE workspaces/facts/:key) through EditFactDrawer — a separate surface with its own inventory. Only CREATION is unique to AddFieldDrawer.

PRE-EXISTING BUG THAT AFFECTS THE REPLACEMENT WORDING. A field created here lands on tab 0 "What she knows", NOT on tab 2 "Who you are" where the add row lives: identityRows filters by `IDENTITY_KEYS = {offer, usp, icp, services, company_address, tone}` (BoldCoreItem.tsx:38, :78, :176-184), which no `field_*` key can ever satisfy, while factRows renders all fields (:152-160). So today the user adds a field from Who-you-are and the row appears on a different tab with the chip "You taught her". SURFACE_SPEC_SETTINGS.md:289 promises an identity field. This is a real defect (PAIR_DIFF.md:175 files the adjacent identity-set gap as 🔴 fix) and it should be settled in the same pass that moves the drawer to ADDFLOW — otherwise the replacement's "row behind the drawer" is on the wrong tab.

STYLE CORRECTIONS TO CARRY WHILE PRESERVING CAPABILITY (all already filed in docs/fidelity/b75/PAIR_DIFF.md, "Add-field drawer" section, and all shared-kit issues that will repeat on add-fact / add-source / add-sender / invite / buy): (1) step indicator becomes two segment bars in the header, not a mono "1 OF 2" in a footer; (2) the primary un-pins and goes inline under the field, full-width forest — the current pinned footer leaves ~598px, 66% of the drawer height, between the input and its own action; (3) step-1 label is "Continue", not "Next"; (4) the step-1 sentence splits into prompt + grey help instead of rendering as a second 15px/700 heading. Kept as-is because canon overrides the prototype atom: the recessed Well, the portalled full-viewport scrim, the 424px rounded panel (SURFACE_SPEC_SETTINGS.md §2; DEC-134, DEC-140, DEC-147).

TWO DEFECTS FOUND WHILE INVENTORYING, worth fixing in the same pass but not capability losses: the step-1 gate no-ops silently below 2 characters (no message, no disabled state — BoldCoreDrawers.tsx:183), and the create button silently overwrites an existing field whose name slugs to the same key, with the same success toast as a fresh create (controller writeWorkspaceField :215-238 has no existence check, unlike editFact and forgetFact which both 404). The second is listed as its own destructive function above and needs the confirm idiom.

## source detail drawer

VERDICT — six of the drawer's functions move onto the row cleanly; the two mutations and their confirm do not, so the container stays (slimmer).

WHY THE KEEP IS NOT A "NON-PROTOTYPE DRAWER". The prototype has this exact anatomy already; it simply never routed a source row to it. `senderDrawer` (Console Bold.dc.html:4839-4864, routed at :5984) is a per-row detail: eyebrow + name + tile, a labelled fact list (`dns` rows), and an action list `sActs` (:4856-4859) whose last entry is danger-toned '✕ Remove this sender'. Recommendation: restyle `SourceDrawer` to that anatomy rather than treat it as an off-prototype container. dc.html:4748's `this.flash('brightsmile.com — 9 pages read, last Tuesday')` is a prototype stub over an unwritten drawer, and its two informational claims (page count, last-read date) are precisely the two facts this inventory moves onto the row.

ONE KIT CHANGE REQUIRED for the LAST READ replacement: `SettingsRow`'s `t:"chip"` variant needs an optional `val` (bold-settings-kit.tsx:698-712 currently makes chip and val mutually exclusive). RowList's render slots are already independent (:724-727), and the prototype template renders both slots independently (dc.html:2343 and :2346) with its own `resp` rows using chip + val together (dc.html:4711-4715). No new atom, just a union widening.

DEFECT FOUND WHILE TRACING (pre-existing, not caused by the re-skin): "Read it again" is offered on EVERY source, but POST /knowledge/sources/:id/retry rejects anything that is not FAILED — 'Only failed sources can be retried' (apps/api/src/knowledge/knowledge.controller.ts:187-189). So on a READY source the footer button always errors, and the ✦ Ada note's 'Read it again' for the empty-yield source (BoldCoreItem.tsx:138-149, chosen because `status === "READY" && chunks === 0`) can never succeed either. Whoever implements the re-skin should either gate the affordance to FAILED sources or widen the endpoint to allow a voluntary re-read; do not carry the dead button forward.

TWO SMALLER HONESTY ITEMS. (1) The drawer has ZERO write fields — no rename, no re-point the URL, no edit of typed text — so there is nothing here for `inline-edit` to take over; yet the add flow's copy promises 'edit the source to change it' (BoldCoreDrawers.tsx:483). Today the only way to change a typed source is remove + re-add. That is a missing capability, not one this inventory can relocate. (2) `sourceLine()` labels a CONNECTOR source 'Typed by you' (BoldCoreItem.tsx:50); unreachable in practice because CONNECTOR creation is rejected at the API (knowledge.controller.ts:82-87, DEC-023), but the same fallthrough will mislabel it the day connectors ship.
